# SupportIQ — Setup Guide & Project Plan

Single source of truth for the whole project. Follow the phases in order and tick each box when done.
Do not move to the next phase until the current one works.

**Theme:** Editorial Analytics — warm paper background, serif headlines, deep teal accent, one insight sentence above each chart, light + dark mode.

---

## 0. Prerequisites

- [ ] Git installed
- [ ] Docker Desktop installed and running
- [ ] Node.js 20+ installed
- [ ] Python 3.11+ installed
- [ ] VS Code with extensions: Python, ESLint, Tailwind CSS IntelliSense, Docker

## 1. Open the project

1. Unzip `supportiq` and open the folder in VS Code (`File > Open Folder`).
2. Open the terminal in VS Code (`` Ctrl+` ``).
3. Initialize Git:
   ```bash
   git init
   git add .
   git commit -m "Initial project structure"
   ```
4. Copy the env file:
   ```bash
   cp .env.example .env
   ```
   Edit `.env` and set a real local password. Never commit `.env`.
   Your `.env` must **not** contain a `DATABASE_URL` line (only `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, `VITE_API_URL`).
   If you change the password after the database container was first created, reset it with `docker compose down -v` then `docker compose up -d db` (this deletes the DB volume; `load_data.py` rebuilds everything).

## 2. Add your data

Put your three CSV files in `data/`:

- [x] `data/agents.csv`
- [x] `data/merchants.csv`
- [x] `data/tickets.csv`

Your dataset (already inspected):

| File | Rows | Key columns |
|---|---|---|
| `agents.csv` | 20 | agent_id, agent_name, tier (L1-L3), primary_category, shift_region, efficiency_multiplier |
| `merchants.csv` | 112 | merchant_id, merchant_name, sector, tier (Foundation/Advanced), region |
| `tickets.csv` | 2,057 | ticket_id, merchant_id, category, sub_category, priority (P1-P4), created_at, assigned_agent_id, first_response_at, closed_at, ttfr_hours, resolution_hours, response_breached, resolution_breached, is_reopened, csat_score (0-1), ... |

Notes: 250 tickets (created 2026-06-29 to 06-30) have no agent, no closed_at and no resolution time. They are the **open backlog**, not bad data. CSAT exists for only 225 tickets and is excluded from averages when null.

## 4. Build phases

- [ ] **Phase 1 — Data:** run the cleaning script and check the report
  ```bash
  pip install pandas
  python scripts/clean_data.py
  ```
  Expected: 20 agents, 112 merchants, 2,057 tickets, 0 duplicates, 0 invalid, 1,807 Resolved / 250 Open. Output goes to `data/clean/`.
- [ ] **Phase 2 — Database:** PostgreSQL service + SQLAlchemy models (agents, merchants, tickets)
  ```bash
  docker compose up -d db
  docker compose ps            # supportiq-db should show "healthy"
  ```
  Tables, foreign keys (tickets -> merchants, tickets -> agents) and filter indexes are defined in `backend/app/database/models.py`.
- [ ] **Phase 3 — Load:** load cleaned data into PostgreSQL
  ```bash
  python -m venv .venv
  .venv\Scripts\activate          # Windows (macOS/Linux: source .venv/bin/activate)
  pip install -r backend/requirements.txt
  python scripts/clean_data.py     # if you have not already
  python scripts/load_data.py
  ```
  Expected: agents 20, merchants 112, tickets 2,057 (Resolved 1,807 / Open 250). Safe to re-run: tables are dropped and reloaded.
  Verify in the DB:
  ```bash
  docker exec -it supportiq-db psql -U supportiq -d supportiq -c "SELECT category, COUNT(*) FROM tickets GROUP BY 1 ORDER BY 2 DESC;"
  ```
- [ ] **Phase 4 — Analytics engine:** Pandas KPIs, SLA, agent performance, dynamic insights (no database needed to preview)
  ```bash
  python scripts/preview_analytics.py        # prints KPIs, tables, insights, recommendations, chart captions
  cd backend
  pip install pytest
  pytest -v                                  # expect 6 passed
  ```
  Expected KPIs on your data: 2,057 tickets, 250 open, 1,807 resolved, SLA compliance 43%, median resolution 26.0h, CSAT 0.75 (225 responses), reopen rate 17.5%.
  How it is built: SQL filters + joins in PostgreSQL (`repository.py`) -> one Pandas frame (`frame.py`) -> calculations (`metrics.py`) -> generated sentences (`insights.py`).
  Metric definitions are documented at the top of `metrics.py`.
- [ ] **Phase 5 — API:** FastAPI endpoints (needs the database loaded in Phase 3)
  ```bash
  cd backend
  uvicorn app.main:app --reload
  ```
  Open http://localhost:8000/docs (interactive API docs) and check:

  | URL | Expect |
  |---|---|
  | `/api/health` | `{"status":"ok"}` |
  | `/api/filters` | dropdown values, dates 2025-01-02 to 2026-06-30 |
  | `/api/dashboard` | `kpis.total_tickets` = 2057, `open_tickets` = 250 |
  | `/api/dashboard?category=Notifications&priority=P1` | smaller numbers (filters work) |
  | `/api/insights` | insights + recommendations arrays |
  | `/api/agents` | 20 agents with SLA, CSAT, reopen rate |
  | `/api/tickets?page=1&page_size=10&sort_by=resolution_hours&sort_dir=desc` | 10 rows, `total` = 2057 |
  | `/api/tickets?search=payments` | only matching tickets |
  | `/api/data-quality` | the cleaning report |

  Filters (same on `/dashboard`, `/insights`, `/agents`, `/tickets`): `date_from`, `date_to`, `category`, `priority`, `status`, `agent_id`, `merchant_sector`, `merchant_region`, `merchant_tier`. Repeat a parameter for several values, e.g. `?priority=P1&priority=P2`.
  The ticket table is paginated, sorted and searched **in SQL** (max 100 rows per page), so the browser never loads thousands of rows.
  Tests (no database needed): `cd backend && pytest -v` -> expect 35 passed.
- [ ] **Phase 6 — Dashboard:** React + Tailwind + Recharts, Editorial Analytics theme
  Keep the database and the API running (Phase 5), then in a **second terminal**:
  ```bash
  cd frontend
  npm install
  npm run dev
  ```
  Open http://localhost:5173. Expect: 8 KPI cards (2,057 total, 250 open, 1,807 resolved), 8 charts each with a one-sentence caption above it, the agent performance table, and a ticket table with search, column sorting and pagination (15 rows per page, server-side).
  Also check: the **Dark mode** button in the sidebar (charts must stay readable), the **Data quality** page, and resize the window (sidebar becomes a top bar on small screens).
  Type-check without starting the server: `npm run build`.
  Filters are added in Phase 7 and the Key Insights / Recommendations panels in Phase 8 (the API already supports both).
- [ ] **Phase 7 — Filters:** date range, category, priority, status, agent, merchant sector, plus Reset filters
  With the API and `npm run dev` running, open http://localhost:5173 and check:
  - Pick **Category = Notifications**: the KPI cards, every chart, every caption, the agent table and the ticket table all change (2,057 becomes 374 tickets).
  - Pick several values in one dropdown (e.g. P1 and P2): they combine as "P1 or P2". Different filters combine as "and".
  - Set a date range (From can't be after To); try **Status = Open** and the SLA/CSAT cards show "–" because open tickets have no resolution yet.
  - Pick a combination that matches nothing: you get a "No tickets match these filters" message instead of an error.
  - **Reset filters** returns to 2,057 tickets.
  Backend check: `cd backend && pytest -v` -> expect 35 passed (includes "SQL filter then Pandas KPIs equals Pandas filter then Pandas KPIs").
- [ ] **Phase 8 — Insights & recommendations:** calculated dynamically, never hardcoded
  Open the dashboard (API + `npm run dev` running). Below the KPI cards you should see **Key insights** (about 11 cards) and **Recommendations** (up to 6, numbered). Check:
  - Unfiltered: Payments & Checkout is the largest category and has the lowest SLA compliance; the volume insight says 2026-06 is high and 250 tickets are still open.
  - Pick **Category = Notifications**: the insight text changes to match that selection.
  - Pick a single agent or **Status = Open**: fewer insights appear (a comparison needs at least 30 resolved tickets per group) instead of misleading ones.
  - Numbers in the text match the KPI cards and charts (same data, same filters).
  The logic lives in `backend/app/analytics/insights.py`: calculate -> compare -> generate sentence. Read it before interviews; every threshold (30 tickets, 5-point SLA gap) is a named constant.
  Backend check: `cd backend && pytest -v` -> expect 35 passed (includes "no NaN/None in any sentence for 29 filter combinations").
- [ ] **Phase 9 — Extras:** CSV export, printable report, CSV upload
  1. Add this line to your `.env` (it is off by default) and **restart the API**:
     ```
     ALLOW_UPLOAD=true
     ```
  2. **Export CSV:** on the dashboard, filter (e.g. Priority = P1), scroll to the Tickets table, click **Export CSV**. The file has every matching ticket (not only the visible page). Open it in Excel and check the row count equals the number shown above the table.
  3. **Print report:** click **Print / save as PDF** at the top of the dashboard and choose "Save as PDF". The sidebar, filters and ticket table are hidden and the page prints in light colours.
  4. **Upload data** (sidebar): choose `agents.csv`, `merchants.csv`, `tickets.csv` from your `data/` folder, click **1. Check files** (nothing changes, you see the cleaning report), then **2. Replace data**. The dashboard should show the same numbers (2,057 tickets). Try removing a column from a copy of a CSV: the check must refuse it and name the missing column.
  Safety: the replace runs in one database transaction (a failed upload leaves the old data untouched), files are limited to 10 MB, and uploads are disabled unless `ALLOW_UPLOAD=true`. There is no login, so keep it `false` on any public deployment.
  The cleaning rules are shared with `scripts/clean_data.py` (`backend/app/data_pipeline/cleaning.py`). Install the new package once: `pip install -r backend/requirements.txt`.
  Backend check: `cd backend && pytest -v` -> expect 35 passed.
- [ ] **Phase 10 — Tests:** backend unit + API integration tests, frontend unit tests (see section 10 for what each one proves)
  ```bash
  pip install -r backend/requirements.txt     # adds httpx for the API tests
  cd backend
  pytest -v                                    # 35 passed without the database; 51 passed with it (API tests need `docker compose up -d db` + `python scripts/load_data.py`)
  cd ../frontend
  npm install                                  # adds vitest
  npm test                                     # 12 passed
  ```
- [ ] **Phase 11 — Docker:** `docker compose up --build` starts the database, API and dashboard
  1. **Stop anything already using the ports:** close the `uvicorn` and `npm run dev` terminals (ports 8000 and 5173). The database container from Phase 2 can stay (same project, same data).
  2. Make sure your `.env` has `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, `VITE_API_URL=http://localhost:8000` and (for the Upload page) `ALLOW_UPLOAD=true`. Your three CSV files must be in `./data`.
  3. From the project root:
     ```bash
     docker compose up --build
     ```
     The first build takes a few minutes. Wait until the log shows `bootstrap: loaded ...` (first start) or `bootstrap: database already holds data` and then `Uvicorn running`.
  4. Open http://localhost:5173 (dashboard) and http://localhost:8000/docs (API). Check: 2,057 tickets, filters, Data quality page, dark mode, refresh on `/data-quality` still works.
  How it works: the **backend** container waits for the database, loads your CSVs only if the database is empty (your uploads are never overwritten on restart), then starts the API. The **frontend** is a production build served by nginx.
  Useful commands:
  ```bash
  docker compose ps                 # all three should be "running" / "healthy"
  docker compose logs backend       # if the dashboard shows an error
  docker compose down               # stop (data is kept)
  docker compose down -v            # stop AND delete the database (next start reloads the CSVs)
  RELOAD_DATA=true docker compose up --build   # (macOS/Linux) force a reload from ./data; on Windows PowerShell set `$env:RELOAD_DATA="true"` first
  ```
  If you change `VITE_API_URL`, rebuild the frontend: `docker compose build frontend`.
  Tests: `cd backend && pytest -v` -> expect 35 passed (51 with the database running).

## 10. Testing guide

Run `pytest -v` in `backend/` and `npm test` in `frontend/`. The goal is **correct numbers**, so most tests compare two independent ways of getting the same answer.

| File | Needs DB? | What it proves |
|---|---|---|
| `backend/tests/test_analytics.py` | no | KPIs on a tiny hand-checked table (SLA 60%, reopen 20%, average CSAT ignores blanks), empty selections never crash, small groups are not compared, KPIs on your real data (2,057 / 250 / 1,807) |
| `backend/tests/test_queries.py` | no (uses SQLite) | Every filter, the search and the sorting return the same rows as plain Pandas; pagination has no overlap; hostile input (`; DROP TABLE`, `' OR '1'='1`, `%`) is harmless; insights contain no `nan`/`None` for 29 filter combinations |
| `backend/tests/test_pipeline.py` | no | Cleaning documents every change, refuses files with missing columns, handles messy values; CSV export is spreadsheet-safe |
| `backend/tests/test_api.py` | **yes** (skipped otherwise) | The real API on the real database: dashboard KPIs equal Pandas on the CSV, filters, pagination, 422 on bad input, CSV row count equals the table total, upload is off by default and refuses a file with a missing column |
| `frontend/src/lib/format.test.ts` | no | Number and date formatting, and that `0` is shown as `0` (not as missing) |
| `frontend/src/services/api.test.ts` | no | Filters become repeated URL parameters (what the API expects), special characters are encoded, API errors become readable messages |

Interview line: *"I tested the analytics by checking one independent path against another: SQL filtering against Pandas filtering, the API against Pandas run directly on the CSV, and a small table whose answers I worked out by hand."*

Not covered on purpose: chart rendering and layout (check visually in light and dark mode). A browser test tool such as Playwright is a good "future improvement".
